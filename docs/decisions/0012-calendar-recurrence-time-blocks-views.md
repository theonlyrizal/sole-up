# 0012: Calendar: event shapes, recurrence, time blocks and views

**Date:** 2026-10-23
**Status:** Accepted

## Context
Phase 4 builds the calendar. [ADR 0007](0007-platform-and-push.md) put calendar events in the MVP as internal events with no external sync. It left four questions for the 4.0 decision gate: recurring events, time blocks, which views ship, and how all-day events are stored. [ADR 0008](0008-dates-and-time-zones.md) fixes the date handling (Temporal through `temporal-polyfill`, local dates as `YYYY-MM-DD`, instants as UTC, IANA zones). [ADR 0011](0011-task-status-planning-priority-estimates.md) sets the rule that nothing moves the user's plans automatically, and [ADR 0005](0005-history-and-audit-log.md)/[ADR 0006](0006-deletion.md) govern audit events and deletion.

The gate recommended the smallest calendar: no recurrence, no time blocks, Week and Agenda views. The user chose full recurrence and full time blocks for v1, FullCalendar as the renderer, and resource views by life area after the Phase 4 checkpoint. This ADR records those answers and the rules derived from them.

## Decision

### Event shapes
- An event is either **timed** or **all-day**, and CHECKs enforce exactly one shape:
  - **Timed:** `start_at`/`end_at` (UTC instants) and `tz`, the IANA zone it was created in. `end_at > start_at`. A timed event may span midnight or several days.
  - **All-day:** `start_date`/`end_date`, PostgreSQL `date` columns with an **exclusive** end (`end_date > start_date`). No instants and no zone, so a time-zone change never moves them (the same rule as `planned_date`).
- The form shows an inclusive end ("24–26 Oct"). The service stores the end plus one day, which is also what FullCalendar expects.
- An event may link to a goal (`goal_id?`) and to a life area (`life_area_id?`), both composite FKs with `ON DELETE SET NULL (column)`. Choosing a goal pre-fills the goal's life area in the form, but the event's own `life_area_id` is what places it in a resource lane.
- `source` defaults to `internal`, and `external_id` stays null. Sync is still out of scope (ADR 0007).

### Recurrence (events and time blocks)
- Recurrence is in v1 for both events and time blocks.
- **Storage:**
  - A recurring item is one **series row**. It holds an `rrule` (the `RRULE` value only, with no `DTSTART`) and the row's own start and end: `start_at` + `tz` for timed items, `start_date` for all-day ones.
  - The start's local wall-clock time in `tz` anchors every occurrence, so a 09:00 meeting stays at 09:00 across DST. Each occurrence lasts the same elapsed duration as the series row.
  - Occurrences are **expanded at query time** for the requested range. They are never stored as rows.
  - Each expansion query has a bounded range, at most 366 days, so a series that never ends costs only what is displayed.
- **Exceptions:**
  - A per-series exceptions table holds the occurrences that differ from the rule. Each row is keyed by `(series_id, original_start)`, unique, where `original_start` is the occurrence's start as the rule generated it: an instant for timed items, a date for all-day ones.
  - An exception either **cancels** that occurrence or **overrides** its fields: times and, for events, title, description, location and links. For time blocks it also holds the occurrence's status.
- **Engine:**
  - [`rrule-temporal`](https://www.npmjs.com/package/rrule-temporal) (MIT, 2.2.8 at the time of writing), wrapped in `src/lib/recurrence.ts`. It is the only file that imports the library, as `src/lib/dates.ts` is for Temporal.
  - The library is Temporal-based and handles `TZID`, `EXDATE`/`RDATE` and range queries.
  - If it turns out to need a global `Temporal` rather than the module import ADR 0008 requires, the implementing chunk stops and asks.
- **Patterns:** the event form has a repeat builder. The server accepts only the rule parts that builder produces, validated with Zod, so the form can always show and edit a stored rule:
  - `FREQ` daily, weekly, monthly or yearly, with `INTERVAL`
  - weekly on chosen weekdays (`BYDAY`)
  - monthly on day N (`BYMONTHDAY`) or on the nth/last weekday (`BYDAY` with an ordinal)
  - yearly on the start's date
  - ends never, after N occurrences (`COUNT`), or on a date (`UNTIL`)

  Arbitrary RFC 5545 rules (`BYSETPOS` combinations, hourly rules) are not accepted.
- **Edit and delete scopes:** a change to an occurrence of a series asks which of three scopes it applies to:
  - **This event:** writes or updates an exception (an override, or a cancellation for delete).
  - **This and following:** in one transaction, ends the old series before the occurrence (`UNTIL`) and starts a new series from it with the change applied.
    - Exceptions after the split move to the new series when their original start is still generated by the new rule. Otherwise they are dropped.
    - The confirmation dialog says when any will be dropped.
    - Deleting with this scope just ends the series.
  - **All events:** edits the series row.
    - A change to the rule or the times drops exceptions that no longer match an occurrence, and the confirmation says so.
    - Deleting with this scope deletes the series and its exceptions.

### Time blocks
- A time block is a planned slot of time **for one task**, kept in its own `time_blocks` table. `task_id` is required, a composite FK with `ON DELETE CASCADE`: deleting a task deletes its blocks, their exceptions and their audit events in the same transaction (ADR 0005).
- A block has no title of its own and shows its task's title.
- It is timed only: `start_at`/`end_at` (UTC) and `tz`, and it lasts at most 24 hours.
- Its resource lane comes from the task's goal's life area: the direct goal, or the milestone's goal. A task with no goal, or a goal with no area, goes in the "No area" lane.
- Blocks repeat with the same builder, the same three edit scopes and the same exceptions mechanism as events.
- **Status:** each block or occurrence is `scheduled` (the default), `done` or `skipped`.
  - The status of a one-off block lives on its row. Each occurrence of a repeating block keeps its own status in an exception row, and an occurrence with no exception is `scheduled`.
  - The user sets the status. A past block still `scheduled` shows neutrally as "Not marked", with no triage section, no red and no reminder.
  - Marking a block `done` never completes its task. The dialog offers "Also complete the task?" as a separate, explicit action.
- **Auto-mark when the task is completed:** in the same transaction as the task's status change:
  - **One-off blocks** of the task that are still `scheduled` and have started (`start_at` at or before the completion time) become `done`.
  - **Repeating blocks:** only the occurrences that started on the user's local day of completion and are still `scheduled` become `done`. Earlier unmarked occurrences stay "Not marked".
  - Future blocks and occurrences are not changed. A repeating series keeps going: its future occurrences show "Task completed" with a one-tap **End series here**, which is the "this and following" delete. Nothing ends a series automatically.
  - Blocks marked `skipped` are never changed. Reopening the task does not revert auto-marked blocks, and cancelling a task marks nothing.
  - Each auto-marked block or occurrence writes its own audit event, which records that the change was automatic.
- **Creating and changing blocks:**
  - from a task's **"Block time"** action: a keyboard-accessible form for the date, start, duration and repeat. Duration defaults to the task's estimate, or 60 minutes when it has none.
  - by **selecting a slot** on the Week or Day grid, then picking a task
  - by **dragging a task** from a task panel beside the Week grid (desktop only)
  - by **dragging a block** to move it or resize it. On a repeating block this asks for the scope.

  The form is always the keyboard and mobile path, so dragging is never the only way to do something.
- **Where blocks show:** Week, Day and Agenda, styled differently from events; Today's timeline, together with today's events; and the task's edit dialog, which lists its upcoming blocks.

### Views and rendering
- **Views in Phase 4:**
  - **Week:** a time grid starting on the user's week-start preference, with an all-day row and timed task deadlines as markers
  - **Day:** the Week view's fallback on mobile
  - **Agenda:** a chronological list for a chosen range, merging events, blocks, timed deadlines and planned tasks
- **No Month view in v1.** The Phase 4 checkpoint decides whether real use needs one.
- **Renderer:** [`@fullcalendar/react`](https://www.npmjs.com/package/@fullcalendar/react) v7 (MIT, 7.1.3 at the time of writing). Its peers are React 17–19 and `temporal-polyfill ^1.0.1`, which matches ADR 0008. In v7 the time-grid, day-grid, list and interaction plugins ship in this one package. Do not install the v6 `@fullcalendar/core` or plugin packages alongside it.
  - It renders only. The server expands occurrences and passes FullCalendar concrete events for the visible range. `@fullcalendar/rrule` is not used: it depends on the classic `rrule` package.
  - Our own dialogs own create and edit, with shared Zod schemas and field-level errors.
  - It is a client component. Theme it with the app's Tailwind tokens in light and dark.
  - The app's accessibility bar applies: axe checks and keyboard navigation must pass on every view. If FullCalendar's grid can't be made to meet it, the implementing chunk stops and asks rather than shipping it.
- **Licensing:** only the MIT package is used. FullCalendar's premium plugins (including its resource views) are not installed, and their code is not copied or adapted.

### Resource views (after the Phase 4 checkpoint)
- A resource is a **life area**. The resource lanes are the user's active life areas plus "No area".
- **Resource columns** (a day grid with one column per area) and **resource timeline** (one row per area across a time range) are built as our own components, after the Phase 4 checkpoint.
- They show events by their `life_area_id` and blocks by their task's goal's area.

### History and deletion
- Calendar events, time blocks and their exceptions follow ADR 0005:
  - Audit events are written in the same transaction and record structured fields only: the shape, times, dates, rule, status, links and scope.
  - Titles, descriptions and locations never go in an audit event.
  - Hard deletes remove the entity's events, and there is no `*.deleted` event (as for tasks, goals and life areas).
  - The exact event names are set in the implementing chunks.
- Deleting a goal or life area clears the link on events with the column-list `SET NULL`. Deleting a task deletes its blocks (above). Deleting the account cascades everything (ADR 0006).

## Alternatives considered
- **No recurrence in v1 (the gate's recommendation):** keeps `calendar_events` one row per event, but repeating commitments would have to be re-created by hand.
- **Weekly-only recurrence, or "this event / all events" scopes only:** less work, but changing a series from a date on would mean rebuilding it by hand. Edit scopes were offered as "all three", "this + all" and "all only".
- **The classic `rrule` library:** the most widely used, but its last release was 2.8.1 in Nov 2023. It works in floating-UTC `Date`s and has known DST pitfalls.
- **Our own RFC 5545 engine on Temporal:** no dependency, but a large edge-case surface.
- **Materialising occurrence rows:** simple range queries, but it needs a horizon, a backfill job and a rewrite on every series edit.
- **Accepting any raw RRULE:** more flexible, but some stored rules couldn't be edited in the form.
- **Time blocks deferred, or task-linked events instead of a table:** one planning model, but no way to reserve time for a task on the grid with its own status.
- **Blocks with an optional task, or a task, goal or area link:** "focus time" without a task, at the cost of more shapes and a title of their own. The user chose a required task.
- **Blocks with no status:** simpler and honest, but no record of how much blocked time was used.
- **Auto-marking every past unmarked occurrence when a task completes:** consistent with one-off blocks, but it would record months of sessions that may not have happened.
- **Ending a repeating block series automatically when its task completes:** tidier, but it changes the calendar behind the user's back (against ADR 0011).
- **A Month view in v1:** cheap to render with FullCalendar, but it's one more view to theme and test, and it gets crowded with repeating items. Left for the checkpoint.
- **Our own week grid instead of FullCalendar:** no dependency and full control of accessibility, but much more work for overlap layout, dragging and resizing.
- **All-day events as midnight-to-midnight instants:** one shape, but they drift across days when the user's zone changes.
- **Inclusive all-day end dates:** read naturally, but every range query and the FullCalendar hand-off needs a +1.
- **Goals as resources, or resource views inside Phase 4:** goals give many sparse lanes, and building the views before the checkpoint would delay dogfooding the basic calendar.

## Consequences
- Two new runtime dependencies, `rrule-temporal` and `@fullcalendar/react`, each behind one boundary: `src/lib/recurrence.ts`, and the calendar client components.
- **New tables:**
  - `calendar_events` and `time_blocks`, each with an exceptions table
  - `calendar_events` gets CHECKs for the two shapes, end after start, and rule presence
  - `time_blocks` gets CHECKs for status and duration
- **Range queries expand series in application code.** Indexes cover the series rows by start, and an index on the series' end (or `UNTIL`) can follow real query plans. A series that never ends is always a candidate in any range, which is cheap at one person's scale.
- **The task service's `changeStatus` now also updates time blocks** when a task is completed, in the same transaction, and a task delete removes the task's blocks and their events.
- Phase 4 grows from five feature chunks to nine before the checkpoint (4.1–4.9), with resource views as 4.10 and 4.11 after it. The implementation plan reflects this.
- **Phase 5 (reminders) must decide** whether event and block occurrences can remind. Reminders for occurrences need expansion, not a stored row per occurrence.
- **Phase 10's export** must include events, blocks and their exceptions.
- `DATA_MODEL.md` (CalendarEvent, TimeBlock), `PRODUCT_SPEC.md`, `ROADMAP.md` and chunks 4.1–4.11 of the implementation plan reflect these rules.
