# 0002: Authentication

**Date:** 2026-10-20
**Status:** Accepted

## Context
The first audience is the developer, but the app will hold sensitive personal data and is meant to be opened to others later. Auth must be public-grade from day one, without inventing cryptography or storing passwords.

## Decision
- **Library:** Better Auth, self-hosted in the Next.js app, storing its tables in our PostgreSQL.
- **Sign-in methods:** Google OAuth and GitHub OAuth. No passwords in v1.
- **Sessions:** database sessions (revocable server-side), not stateless JWTs.
- **Account linking:** only when the provider reports a verified email that matches.
- **Authorization:** every Server Action and route handler calls `requireUser()` first; every query is scoped by `user_id` (see the ownership pattern in [IMPLEMENTATION_PLAN.md](../IMPLEMENTATION_PLAN.md#ownership-pattern)).
- The user's ID is a UUID owned by our `users` table, not the provider's subject.

## Alternatives considered
- **Auth.js (NextAuth):** viable, but Better Auth's database sessions and linking controls fit better.
- **Hosted auth (Clerk, Auth0):** less code, but adds a third party holding identity data and a paid dependency.
- **Email/password:** requires password storage, reset flows and breach handling; not needed for v1.
- **Passkeys:** deferred to the invited beta.

## Consequences
- Users need a Google or GitHub account.
- OAuth apps must be created by the developer (agents never create them or handle secrets).
- Account deletion must also revoke sessions and remove linked accounts.
