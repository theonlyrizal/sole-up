# Chunk 10.7 performance evidence

Measured on 2026-11-11 with local Docker PostgreSQL 18.3, shared buffers 128 MB, work memory 4 MB and random page cost 4. The benchmark represents a year of sustained personal use across 24 synthetic accounts. Each account has six life areas, 18 goals, 54 milestones, 2,920 tasks, nine habits and 183 notes. The date span is 2025-11-12 through 2026-11-11. Tasks mix completed, cancelled, inbox, planned, timed and all-day deadlines, and reschedules. Habits mix three cadences, quantity/check measures, schedule versions, skips, partial quantities, gaps, pauses and archives. Events and blocks include weekly recurrence and cancelled occurrences. Notes include bodies, tags and goal/task links. Reviews cover completed weeks.

The database contains 70,080 tasks, 190,907 audit events, 41,003 habit logs, 17,520 event rows, 35,040 block rows, 4,392 notes and 1,224 reviews. Recurrences expand when the application reads them.

## Method

`scripts/performance/workload.ts` invokes existing application read models through Vite, using the same aliases and server-only no-op as the test harness. The workload captures 85 distinct SQL-and-parameter pairs across 25 view scenarios. Shared queries retain every associated view label. Each captured SELECT runs with `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` once to warm it, followed by five measured executions. Each report records all five execution/planning timings, the full median execution plan, SQL, synthetic bind values, query hash, PostgreSQL settings and installed index definitions. The fixture account's audit payloads are validated against the application's registry first. Preference initialization runs normally and its idempotent insert is excluded from EXPLAIN.

The baseline database was migrated through 0022, seeded and vacuum-analyzed. After capturing the baseline, migration 0023 was applied through `pnpm db:migrate` and the identical workload was captured again with the same data and date. Query hashes, SQL and parameters match across all 85 pairs. Times below are warm database executor times. Browser rendering, application-side recurrence/consistency computation, network transfer and production Neon cold starts require separate measurements.

The full plans and samples are in [before](10.7-before.json) and [after](10.7-after.json).

## Index decisions

| Change in migration 0023                                                           | Query ID prefix | Before ms | After ms | Shared hits before | Shared hits after |
| ---------------------------------------------------------------------------------- | --------------- | --------- | -------- | ------------------ | ----------------- |
| Replace `audit_events_user_id_entity_idx` with `audit_events_user_entity_time_idx` | `1ca0c97f09`    | 74.808    | 47.345   | 116,229            | 67,571            |
| Add `audit_events_task_planned_date_idx`                                           | `4a2e4e71f8`    | 1.361     | 0.105    | 356                | 19                |

The Insights overdue trend reconstructs four weekly snapshots. Its baseline plan performs 11,248 lookups for each of two lateral audit-history queries, filters `occurred_at` after scanning each entity's events, and sorts each lookup by `occurred_at, id`. The replacement index keeps `(user_id, entity_type, entity_id)` and extends it with `(occurred_at, id)`. Both after-plan lateral lookups use the replacement with the time bound in `Index Cond`, and their inner sorts disappear. This supports removing the shorter index while preserving its equality prefix. The remaining aggregate sort serves the four snapshots.

Review's `plannedTaskIds` baseline filters thousands of task events by JSON planning date after reading them. Its after plan uses `audit_events_task_planned_date_idx` with the user and both date bounds in `Index Cond`. The index stores `(user_id, (changes -> 'plannedDate' ->> 'to'), entity_id)` for task-created/task-planned events. The result contains 41 events before deduplication in both plans. Its predicate and expression match the read model. ISO local dates retain their text ordering.

Every index addition and removal in 0023 is covered by these two before/after plan pairs. The reports retain definitions of both the removed and replacement indexes. Other existing indexes are retained because this workload supplies no removal evidence for them.

## Follow-up supported by a plan

Review summary query `9c000d039a` measured 65.771 ms before and 64.957 ms after, with 19,695 shared hits in both plans. Its goal-activity subplan scans all 70,080 tasks six times and filters a `coalesce(tasks.goal_id, milestones.goal_id)` expression across a left join. This requires investigating the query shape and owner predicates. The index-only scope of this chunk leaves that work for a later change. Search spends time computing full-text ranks and headlines with existing search indexes selected, and supplies no evidence for another index here.

## Running the tools

From PowerShell in the repository, using the Compose local development credentials, run the following once to create the scratch database.

```powershell
docker compose up -d --wait
docker compose exec -T postgres createdb -U soleup soleup_perf
```

Then run the current migration, seed and capture commands. Shell environment values take precedence over `.env.local`. The benchmark also reads the application's existing local environment configuration.

```powershell
$env:DATABASE_URL = 'postgresql://soleup:soleup@localhost:5432/soleup_perf'
pnpm db:migrate
pnpm db:seed:performance --as-of=2026-11-11 --users=24
pnpm db:explain:performance --as-of=2026-11-11 --out=performance-current.json
Remove-Item Env:DATABASE_URL
```

Both tools refuse `NODE_ENV=production`, remote hosts and database names outside the local `_perf` namespace. Seeding replaces the reserved synthetic identities in one transaction under an advisory lock and preserves other accounts. Repeating it with a smaller user count removes excess reserved fixtures. Concurrent benchmark and seed runs coordinate on the same lock. A seed failure rolls back the replacement. The benchmark requires its as-of date to match the seed's date. Accounts use `example.invalid` addresses, reminders are disabled, and the script creates no OAuth accounts, sessions or push subscriptions.
