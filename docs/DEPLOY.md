# Deploying SoleUp

Production runs on two free services, chosen in chunk 0.14:

| Part | Service | Plan | Region |
|---|---|---|---|
| Web app (Next.js, one Node process) | [Render](https://render.com) web service, from [`render.yaml`](../render.yaml) | Free | Singapore |
| Database (PostgreSQL) | [Neon](https://neon.com) | Free | AWS ap-southeast-1 (Singapore) |

Both are free and need no card. This follows [ADR 0003](decisions/0003-hosting-and-jobs.md) (one Node host, managed Postgres). Read "Free-plan limits" before relying on it.

In the steps below, `<APP_URL>` is the service's public URL, for example `https://soleup.onrender.com`. It has no trailing slash.

## How a deploy works

1. A commit lands on `main` (a merged PR).
2. GitHub Actions CI runs on it. Render waits for the checks to pass (`autoDeployTrigger: checksPass`). A red commit is never deployed.
3. Render runs the build command:
   1. `corepack enable`. pnpm's version comes from `packageManager` in `package.json`, Node's from `.nvmrc`.
   2. `pnpm install --frozen-lockfile`.
   3. `pnpm build`.
   4. **`pnpm db:migrate:deploy`, the release step.** It applies pending migrations in one transaction, so all of them apply or none do ([`scripts/db-migrate-deploy.mts`](../scripts/db-migrate-deploy.mts)).
4. Render starts the new version with `pnpm start` (`next start` on `$PORT`). The server validates its environment at boot and exits with a list of problems if any are wrong.
5. Render switches traffic only after `GET /api/health` answers 200, which needs the database too. Until then the previous version keeps serving.

If any step fails, the deploy fails and the previous version keeps running. A failed migration leaves the database as it was.

**Why migrations run in the build:** Render's `preDeployCommand` is for paid instances only. It runs at the same point in the sequence: after the build, before the new version takes traffic, while the old version still serves. On a paid plan, move `pnpm db:migrate:deploy` from `buildCommand` to `preDeployCommand`.

**Migrations must be backward compatible** with the version still serving traffic, and with the version you may roll back to. Use expand, then contract: add the column or table in one deploy, then remove the old one in a later deploy once nothing reads it. Never rename or drop in the same deploy that stops using something.

## Environment variables

Set these on the Render service (**Environment**). Secrets are entered in the dashboard only. Never commit them.

| Variable | Value | Notes |
|---|---|---|
| `DATABASE_URL` | Neon **direct** connection string (not "Pooled"), with `sslmode=verify-full` | See "Provision Neon". The app keeps one connection pool in one long-running process, so it doesn't need Neon's pooler. Migrations need a direct connection anyway. |
| `BETTER_AUTH_SECRET` | Generated by Render (`generateValue`) | 256 random bits. Changing it signs everyone out. |
| `BETTER_AUTH_URL` | `<APP_URL>` | Must match the URL users visit exactly. OAuth callbacks are built from it. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | From the **production** Google client | Set both or neither. |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | From the **production** GitHub OAuth app | Set both or neither. |
| `REMINDER_SWEEP_SECRET` | 32 random bytes you generate (see "Reminder sweep") | Required: the app won't boot without it. Also entered in the cron-job.org job. |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` | A pair you generate (see "Web Push keys") | Required at boot; the app checks they belong together. |
| `VAPID_SUBJECT` | `mailto:<your address>` or an `https://` URL | Required. Push services may use it to contact you about your pushes. |
| `COREPACK_ENABLE_DOWNLOAD_PROMPT` | `0` | Set by `render.yaml`. Lets corepack fetch pnpm without a prompt. |
| `NEXT_TELEMETRY_DISABLED` | `1` | Set by `render.yaml`. |

Don't set:

- **`NODE_ENV`.** With `NODE_ENV=production`, `pnpm install` skips the dev dependencies the build needs. `next start` runs in production mode regardless.
- **`TEST_DATABASE_URL` or `SOLEUP_TEST_SIGN_IN`.** These are for tests only.
- **`PORT`.** Render sets it.

`.env.example` lists the same variables with local values.

## OAuth production callback URLs

Create **separate production** OAuth credentials. Don't reuse the local ones: each environment has its own callback URL and secret. The callback is always `<BETTER_AUTH_URL>/api/auth/callback/<provider>`.

| Provider | Production callback URL |
|---|---|
| Google | `<APP_URL>/api/auth/callback/google` |
| GitHub | `<APP_URL>/api/auth/callback/github` |

**Google** ([Google Cloud console](https://console.cloud.google.com)):

1. Create a project `soleup-prod` and select it.
2. **Google Auth Platform → Get started.** App name `SoleUp`, your support email, audience **External**, your contact email. Accept the policy.
3. **Audience:** keep the publishing status **Testing** and add your Google account as a **test user**. Only test users can sign in. That suits dogfooding, and it avoids publishing a consent screen without a privacy policy (chunk 10.3).
4. **Data Access:** add nothing. The app asks only for `openid`, `email` and `profile`.
5. **Clients → Create client → Web application**, named `SoleUp production`:
   - **Authorized JavaScript origins:** `<APP_URL>`
   - **Authorized redirect URIs:** `<APP_URL>/api/auth/callback/google`
6. Copy the client ID and secret into Render's `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`.

**GitHub** ([Developer settings → OAuth Apps](https://github.com/settings/developers) → **New OAuth app**):

- **Application name:** `SoleUp`
- **Homepage URL:** `<APP_URL>`
- **Authorization callback URL:** `<APP_URL>/api/auth/callback/github`
- Leave **Enable Device Flow** unchecked.

Then **Generate a new client secret**, and copy the ID and secret into Render's `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`.

If the URL ever changes (a custom domain, a renamed service), update `BETTER_AUTH_URL` and both callback URLs together.

## First-time provisioning

Do these in order. Each step says what to check before moving on.

### 1. Provision Neon

1. Sign up at [neon.com](https://neon.com) (Free plan, no card).
2. **Create project:** name `soleup`, Postgres version **18** (17 is fine if 18 isn't offered; the schema needs 15 or later), region **AWS Asia Pacific (Singapore)**. The default database `neondb` and its owner role are fine.
3. **Connect** on the project dashboard: choose the `production` (default) branch and turn **Connection pooling off**. Copy the connection string. Its host must **not** contain `-pooler`.
4. In the string, replace `sslmode=require` with `sslmode=verify-full`. Keep `channel_binding=require` if it's there. `verify-full` checks the server certificate. The `pg` driver warns about `require` and will weaken it in its next major version. This string is `DATABASE_URL`. Keep it in your password manager, not in a file in the repo.
5. **Check the restore window:** **Settings → Instant restore** (or **Backup & Restore** on the branch). Free shows **6 hours**, the plan's maximum. See "Backups and point-in-time recovery".

### 2. Create the Render service

1. Sign up at [render.com](https://render.com) with GitHub (no card for Free).
2. **New → Blueprint.** Connect the `soleup` repository and pick branch `main`. Render reads `render.yaml` and proposes one free web service, `soleup`, in Singapore.
3. Render prompts for each `sync: false` variable. Enter `DATABASE_URL` now. Leave `BETTER_AUTH_URL` and the OAuth values empty if you don't know the URL yet. The first deploy then fails at boot ("BETTER_AUTH_URL is missing"), which is expected.
4. Click **Apply.** The service's URL appears at the top of its page. That URL is `<APP_URL>`.
5. **Environment:** set `BETTER_AUTH_URL` to `<APP_URL>`.
6. Create the production OAuth credentials (above) with `<APP_URL>`, enter the four OAuth variables, and **Save, rebuild and deploy**.
7. **Check:** the deploy log shows `db:migrate:deploy: done.`, then the health check passes. `<APP_URL>/api/health` returns `{"status":"ok","database":"ok"}`.

### 3. Verify production (chunk 0.14 "done when")

1. Open `<APP_URL>`, sign in with Google, then sign out and sign in with GitHub. Confirm your time zone.
2. Go to **Goals → Life areas** and create an area, for example `Health`.
3. Trigger another deploy: **Manual Deploy → Deploy latest commit**, or merge the next PR. Wait for it to go live.
4. Reload **Life areas.** `Health` is still there.

## Reminder sweep

Reminders have no worker on the free plans ([ADR 0013](decisions/0013-reminders-sweep-and-delivery.md)). [cron-job.org](https://cron-job.org) (free) calls `POST <APP_URL>/api/reminders/sweep` every 15 minutes, with the secret in an `Authorization: Bearer` header. Each call sends the reminders due before the next one, so reminders arrive up to 15 minutes early. A call without the right secret gets `401` and does nothing. The route reads no body and answers only counts, for example `{"counts":{"claimed":2,"sent":1,"skipped":1,"skippedByReason":{"stale":1,"disabled":0,"no_device":0},"failed":0,"held":0,"retrying":0},"durationMs":38}`.

**`REMINDER_SWEEP_SECRET` is required at boot.** Set it on Render **before** the deploy that introduces it (chunk 5.1). Otherwise that deploy fails its boot check and the previous version keeps serving until you add it and redeploy.

### 1. Create the secret and set it on Render

1. Generate 32 random bytes on your own machine. Either command works:

   ```bash
   node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
   ```

   ```bash
   openssl rand -base64 32
   ```

   The first prints 43 characters, the second 44. The app refuses anything shorter than 43. Use a new value for production. Don't reuse your `.env.local` one.
2. Keep it in your password manager. Never put it in a file in the repo, a PR, an issue or a chat.
3. Render → the `soleup` service → **Environment → Add Environment Variable:** key `REMINDER_SWEEP_SECRET`, the value from step 1. **Save, rebuild and deploy** (or **Save only** when the deploy that needs it hasn't landed yet).
4. **Check:** the deploy goes live, and this returns `401` (no secret sent):

   ```bash
   curl -i -X POST <APP_URL>/api/reminders/sweep
   ```

`render.yaml` declares the variable with `sync: false`, so a Blueprint sync asks for it rather than generating one: you need to know the value to enter it in cron-job.org.

**Rotating it:** generate a new value, update Render (**Save, rebuild and deploy**), then update the cron-job.org header straight away. Calls in between get `401`, so at most one sweep is missed and the next catches up.

### 2. Create the cron-job.org job

1. Sign up at [cron-job.org](https://cron-job.org) (free, no card) and confirm your email.
2. **Dashboard → Cronjobs → Create cronjob.** On the **Common** tab:
   - **Title:** `SoleUp reminder sweep`
   - **URL:** `<APP_URL>/api/reminders/sweep`
   - **Enable job:** on
   - **Execution schedule:** **Every 15 minutes** (custom: minutes `0,15,30,45`, every hour, day and month).
   - **Notify me when:** execution fails, and the job is disabled because of too many failures.
3. On the **Advanced** tab:
   - **Time zone:** any. A 15-minute schedule is the same in every zone.
   - **Request method:** `POST`. Leave the request body empty.
   - **Headers → Add:** key `Authorization`, value `Bearer <REMINDER_SWEEP_SECRET>`: the word `Bearer`, one space, then the secret.
   - **Timeout:** the longest allowed. cron-job.org's FAQ gives every job **30 seconds**, after which it closes the connection and records a failure.
   - **Treat redirects with HTTP 3xx status code as success:** off. The route never redirects, so a redirect means a wrong URL.
   - **Save responses in job history:** on. Responses hold only counts, which helps when checking the job.
4. **Create**, then **Test run** (or wait for the next quarter hour). The run history shows `200 OK` and the counts.
5. **Check in Render's logs** (search `Reminder sweep`): each call writes one line, `"msg":"Reminder sweep finished"`, with `sweepStartedAt`, `counts` (claimed, sent, skipped with `skippedByReason`, failed, held, retrying) and `durationMs`. A call with a bad secret writes `"Reminder sweep refused: bad secret"` instead. The secret and reminder content are never logged.

Field names in cron-job.org's console may differ slightly from the ones above; the settings that matter are the URL, `POST`, the `Authorization` header, every 15 minutes and the timeout.

cron-job.org disables a job after many failures in a row (its FAQ gives more than 25 as an example), and it emails you when it does if you turned that notification on. While the job is off, no reminders go out. Nothing else in the app breaks. Each finished sweep records its time, and **Settings → Reminders warns when no sweep has run for over an hour**, so a stopped job shows up in the app too. When the job runs again, the first sweep sends what is still useful and skips the rest as stale.

### Failed reminders

A reminder that fails 3 times in a row (an error other than an expired subscription) is marked `failed` with its error code. There is no admin page; list them from your machine:

```bash
pnpm reminders:failed
```

It prints a table of error codes with counts in the last day, the last week and older, and how long ago the newest and oldest failed. No titles, users or IDs. It reads `DATABASE_URL` from the shell or `.env.local`, so for production set `DATABASE_URL` in your shell to the Neon direct connection string first (it only reads). Codes are `http_<status>` from the push service, `timeout`, `network` or `invalid`.

### 3. Production check (chunk 5.1)

For one hour, Render's logs show a `Reminder sweep finished` line every 15 minutes (four lines), and cron-job.org's history shows four successful runs.

**Cold starts:** the free service sleeps after 15 idle minutes, and the sweep comes every 15 minutes, so a call can find the app asleep. Waking takes about a minute, which is longer than cron-job.org's 30 seconds. The run is then recorded as failed (timeout), and its log line may appear later or not at all. Missed reminders go out on the next sweep (ADR 0013). If the history shows regular timeouts, the fallback in ADR 0013 is a second cron-job.org job every 10 minutes to a route that doesn't touch the database, to keep the app awake without keeping Neon awake. Don't use `/api/health` for it: it queries the database.

### Free-plan budget

- **Render:** 750 free instance hours a month. Sweeps every 15 minutes keep the service awake almost all the time: about 744 hours in a 31-day month. That is the whole allowance, so no other free Render service can share this workspace. Check the free usage in Render's workspace billing page during the first month.
- **Neon:** each sweep wakes the compute, which then stays up 5 minutes before it suspends. That is about 62 of Free's 100 CU-hours a month (ADR 0013), leaving about 38 for your own use. See "Watching Neon's compute" below.

### Watching Neon's compute (Phase 5 checkpoint)

Neon Free allows **100 CU-hours per project per month** (checked on Neon's plans page, 2026-10-29). A CU-hour is the compute size times the hours it runs: the smallest size, 0.25 CU, for 4 hours is 1 CU-hour. The compute suspends after 5 idle minutes, and that can't be turned off on Free. **When the allowance runs out, the compute is suspended until the next month**, which takes the whole app down (no data is lost).

**How to read it:**

1. Neon console → the SoleUp project → **Overview**. The **Usage** panel shows **Compute** for this project since the start of the current billing period.
2. For the plan summary, open your organization from the profile menu (top right) → **Billing**.
3. The figures lag by about an hour.

**What to do with it:** during the Phase 5 checkpoint week, write down the Compute figure on the first and last day, and divide by the days between to get a daily rate. A month at that rate is about 30 times it. Expect about 2 CU-hours a day from sweeps alone.

**Threshold: about 80 CU-hours a month.** If the month is heading past that, act before it runs out: widen the sweep interval (cron-job.org schedule; reminders then arrive earlier, and `SWEEP_INTERVAL_MINUTES` in `src/lib/reminders.ts` must match it) or move to paid hosting. Either is a change to ADR 0013, so record it in a new ADR.

## Web Push keys

Push notifications are signed with a VAPID key pair (chunk 5.3). **All three variables are required at boot**, so set them on Render **before** the deploy that introduces them; otherwise that deploy fails its boot check and the previous version keeps serving.

1. On your own machine, in the repo after `pnpm install`:

   ```bash
   pnpm exec web-push generate-vapid-keys
   ```

   It prints a public key (87 characters) and a private key (43). Use a new pair for production, not your `.env.local` one.
2. Keep the private key in your password manager. Never put it in a file in the repo, a PR, an issue or a chat. The public key isn't secret (browsers receive it), but keep the pair together.
3. Render → the `soleup` service → **Environment:** add `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` (`mailto:` plus an address you read). **Save only** if the deploy that needs them hasn't landed yet, otherwise **Save, rebuild and deploy**.
4. **Check:** the deploy goes live; on Settings → Notifications, **Turn on notifications**, then **Send test notification** arrives.

**Rotating the pair** invalidates every subscription: browsers refuse pushes signed with a different key. After rotating, each device must turn notifications on again (Settings replaces the old subscription automatically). Only rotate if the private key leaked.

## Rollback

**Code rollback (no schema change involved):**

1. On the Render service, open **Events** (or **Deploys**), find the last good deploy, and click **Rollback → Rollback to this deploy**.
2. Render redeploys that deploy's stored build. It does **not** rebuild, so **no migrations run**.
3. A rollback from the dashboard **turns auto-deploy off.** Fix forward on `main`, then turn it back on under **Settings → Build & Deploy → Auto-Deploy: After CI checks pass**.

**When the bad deploy included a migration:** the database keeps the new schema after a code rollback. If the migration was backward compatible (expand only), the code rollback is enough. If it wasn't, fix forward with a new migration. Migrations are forward-only: there are no down migrations. Restore the database (below) only if data was damaged, because a restore also loses every write since the restore point.

## Backups and point-in-time recovery

**What Neon Free gives you:** point-in-time restore of the root branch to any moment in the last **6 hours** (capped at 1 GB of change history). Free has no longer window and no daily snapshots. A problem noticed after 6 hours can't be undone from Neon alone.

**Safety net, weekly and before any risky migration:** a logical backup to your own machine. It needs Docker locally (the same `postgres:18.3-alpine` image as `docker-compose.yml`, whose `pg_dump` matches the server's major version):

```bash
docker run --rm -e DATABASE_URL postgres:18.3-alpine sh -c 'pg_dump --format=custom --no-owner --no-privileges "$DATABASE_URL"' > soleup-$(date +%Y%m%d).dump
```

Run it with `DATABASE_URL` set in your shell to the production string. The dump holds every user's personal data. Store it encrypted (for example in your password manager's file storage or an encrypted disk), never in the repo, and delete old dumps you no longer need.

**Check that PITR works.** Do this once at provisioning, then again before chunk 10.6's restore drill. It changes nothing:

1. Neon console → **Branches → Create branch.** Parent `production`, **Include data up to: a specific time**, set to about 1 hour ago (after your first life area existed). Name it `pitr-check`.
2. Open **SQL Editor** on `pitr-check` and run `select count(*) from life_areas;`. The count reflects that time.
3. Delete the `pitr-check` branch.

## Restore

**From point-in-time (within 6 hours):**

1. Decide the restore timestamp (UTC), just before the damage. Optionally preview it with **Time Travel Assist** (read-only queries at a past time).
2. Neon console → the `production` branch → **Backup & Restore → Restore from history.** Pick the timestamp, then **Next → Restore**.
3. Neon keeps the pre-restore state as a branch named `production_old_<timestamp>`. Keep it until you're sure, then delete it.
4. The connection string doesn't change. Open connections drop briefly and the app's pool reconnects. Check `<APP_URL>/api/health`.
5. The restored database has the `drizzle.__drizzle_migrations` journal from that time. If the code now expects newer migrations, the next deploy re-applies them. Render's **Manual Deploy → Deploy latest commit** forces one.

**From a `pg_dump` file (older than 6 hours, or Neon unavailable):**

1. In Neon, create an empty database on the `production` branch (**Databases → New database**, for example `soleup_restored`, owned by the same role). Copy its **direct** connection string (with `sslmode=verify-full`) into `RESTORE_URL` in your shell.
2. Restore into it:

   ```bash
   docker run --rm -i -e RESTORE_URL postgres:18.3-alpine sh -c 'pg_restore --no-owner --no-privileges --dbname="$RESTORE_URL"' < soleup-YYYYMMDD.dump
   ```

3. Check it: connect with the SQL Editor and spot-check `select count(*) from users;` and `from life_areas;`.
4. Point Render's `DATABASE_URL` at it and **Save, rebuild and deploy.** The release step applies any migrations newer than the dump.
5. Writes made after the dump are lost. Sessions created after it are gone too, so users sign in again.

## Logs and monitoring

- **Logs:** Render's **Logs** tab shows the app's JSON lines (pino, redacted; see README > Logging and errors). Search by `requestId` from a user's error reference, or by an error's digest. Logs aren't shipped anywhere else. Render keeps them for a limited period that depends on the workspace plan.
- **Request IDs:** the app generates its own `x-request-id` for every request and ignores any incoming value, including any from Render's proxy.
- **Health:** Render checks `/api/health` continuously while the service is awake.
- **Client IPs and rate limits:** Better Auth's rate limiter reads the client IP from `x-forwarded-for`, and only when that header holds exactly one address. Next.js fills the header from the socket when it's absent, so a direct request is still counted per IP. A request whose header holds several addresses has no usable IP, so it goes into one shared bucket. Better Auth then logs, once per process: `Rate limiting could not determine a client IP`. A client that sends its own header can trigger this (Render appends to it), and that only throttles the shared bucket. But if Render's proxy itself adds an address to every request, all users share 10 sign-ins a minute. After the first deploy, sign in once and search the logs for that warning. If it appears on your own normal sign-in, set `advanced.ipAddress` in `src/server/auth/auth.ts` for Render's proxy.

## Free-plan limits

- **The app sleeps after 15 idle minutes.** The first request after that takes about a minute while Render wakes it. 750 instance hours a month are free; a sleeping service uses none.
- **Neon Free** suspends its compute after 5 idle minutes (wake-up is well under a second). It allows 0.5 GB of storage per project and a 6-hour restore window.
- **No background worker.** Render runs workers on paid plans only, and a sleeping web service can't fire reminders on time. Decision gate 5.0 kept the free plans: an external cron (cron-job.org) calls a reminder sweep route every 15 minutes, so reminders may arrive up to 15 minutes early ([ADR 0013](decisions/0013-reminders-sweep-and-delivery.md)). See "Reminder sweep" for the setup and its cost in free hours.
- **Build minutes and bandwidth** have monthly allowances. Without a card, Render suspends the service when they run out instead of billing.

## Moving to a paid plan later

- Render: change `plan` in `render.yaml` and move the release step to `preDeployCommand`. The `region` stays Singapore; it can't be changed.
- Neon: raise the history window under **Settings → Instant restore** (up to 7 days on Launch).
